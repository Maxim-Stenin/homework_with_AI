# Автотесты: pytest + Playwright

Раннер выбран человеком в сессии 4 и **не меняется без отдельного вопроса**.
Selenium рассматривался и отклонён: без встроенного ожидания элементов падающий тест
начинает мигать по таймингу вместо того, чтобы падать по дефекту.

Готовые рецепты кода — в [references/patterns.md](references/patterns.md).
Здесь — правила и метод.

## Главное правило

**Тест, написанный на найденный дефект, обязан падать.** Красный прогон — это и есть
требуемый результат и доказательство находки. Зелёный тест на месте реального дефекта
означает одно из двух: тест ничего не проверяет либо объект был изменён. Оба варианта
хуже отсутствия теста.

Отсюда прямой запрет: **если тест падает, чинится тест или уточняется ожидание,
но никогда не объект.** `app/index.html` не правится ни на символ — ни ради зелёного
прогона, ни ради `data-testid`, за который удобно зацепиться. Неудобная для автоматизации
разметка — сама по себе находка, её место в замечаниях, а не в правке файла.

`xfail` для дефектных тестов **не используется.** Он превращает красный прогон в жёлтый
и прячет ровно то, что мы сдаём. Тесты на дефектах живут отдельным файлом
`tests/test_defects.py` и падают честно; в отчёте объясняется, что каждое падение —
это находка, а не поломка.

## Установка

Перед каждой командой установки — спросить человека (требование сессии 4).

```bash
pip install pytest pytest-playwright
```

```bash
python -m playwright install chromium
```

Вторая команда качает браузер из сети (~120 МБ). Каждая установка — запись в `TOOLS.md`.

## Структура

```
tests/
├── conftest.py          # константы, фикстуры стенда, страницы, чистого хранилища
├── helpers.py           # добавление записи, чтение таблицы, чтение итогов и легенды
├── test_form.py         # валидация формы: сумма, категория, дата, тип
├── test_totals.py       # арифметика итогов, округление, согласованность
├── test_chart.py        # доли, легенда, пустые состояния диаграммы
├── test_csv_export.py   # выгрузка и экранирование
├── test_csv_import.py   # загрузка, подтверждение, битые файлы, валидация при импорте
├── test_roundtrip.py    # цикл «сохранить → загрузить»
├── test_mobile.py       # 375×812
├── test_defects.py      # тесты на подтверждённые баги — падают намеренно
└── fixtures/            # заранее подготовленные CSV, в том числе испорченные
```

Тесты живут в `tests/`, **не в `app/`**: в `app/` ровно один файл, появление там второго
— повод остановиться и спросить.

## Запуск

```bash
python -m pytest tests -v
```

```bash
python -m pytest tests -v --tb=short -k "not defects"
```

Второй вариант — прогон без заведомо падающих: удобно при разработке тестов, но
**в отчёт идёт полный прогон**, вместе с падениями.

Стенд поднимается командой из `AGENTS.md` либо фикстурой в `conftest.py`.
Адрес и порт — одна константа в `conftest.py`, второй раз в тестах не хардкодятся.
`file://` под Playwright заблокирован: только через стенд.

## Слои проверок

Три слоя, и они дают разное. Тест, работающий только на первом, доказывает мало.

1. **Наблюдаемое поведение** — что видит пользователь: строки таблицы, числа в итогах,
   подписи легенды. Основной слой.
2. **Инварианты данных** — то, что обязано выполняться при любом входе: сумма строк
   таблицы равна итогу; доли легенды дают 100 %; число строк меняется ровно на единицу
   при добавлении. Инварианты ловят дефекты, для которых никто не написал отдельного теста.
3. **Побочные сигналы** — ошибки в консоли, необработанные исключения страницы,
   отсутствие сетевых запросов. Собираются фоном и проверяются в конце каждого теста.

## Параметризация вместо копирования

Двадцать почти одинаковых тестов на валидацию суммы — это двадцать мест, где можно
разойтись. Классы эквивалентности и границы из каталога ручных проверок ложатся
в `@pytest.mark.parametrize` таблицей: вход, ожидание, идентификатор случая. Тогда
добавить граничное значение стоит одну строку, а имя упавшего случая читается
в выводе `pytest` без расшифровки.

Правило: **один тест — одна причина падения.** Если тело теста проверяет и отказ формы,
и текст сообщения, и состояние итогов, при падении непонятно, что именно сломалось.
Разносить либо на отдельные тесты, либо на явные шаги с понятными сообщениями `assert`.

## Проверка отказа — самое частое место, где тест лжёт

Тест, который проверяет только появление сообщения об ошибке, пропустит приложение,
которое ругается и всё равно создаёт запись. Проверка отказа состоит из трёх частей,
и первые две обязательны:

1. число строк таблицы до и после совпадает;
2. итоги не изменились;
3. сообщение об ошибке показано.

То же для отказа от подтверждения при удалении и при загрузке CSV: сначала убедиться,
что данные целы, и только потом — что диалог отработал.

## Селекторы

Строятся **по той разметке, которая есть**. Дописывать в объект атрибуты под тесты
запрещено. Порядок предпочтения:

1. Роль и доступное имя — `get_by_role("button", name="Добавить")`. Устойчивее всего
   и заодно косвенно проверяет осмысленность разметки.
2. Метка поля, видимый текст — `get_by_label`, `get_by_text`.
3. Существующие `id` и классы — `page.locator("#amount")`.
4. Позиционные и цепочечные CSS-селекторы — последнее средство. Такой селектор ломается
   от любой перестановки; если пришлось к нему прибегнуть, **записать это как замечание
   о тестопригодности**, а не молча жить с ним.

Селекторы собираются в одном месте (`helpers.py` или константы `conftest.py`), а не
рассыпаются по файлам: разметка объекта не изменится, но читаемость падения зависит
от того, видно ли, за что тест цеплялся.

## Детерминизм

Нестабильный тест хуже отсутствующего: он приучает не верить красному.

- **Никаких `sleep`.** У локаторов Playwright ожидание встроено; там, где значение
  появляется асинхронно, — `expect(...)`, а не `assert` по снятому значению.
- **Чистое состояние перед каждым тестом.** Всё состояние живёт в `localStorage`;
  очистка делается **до** загрузки страницы, иначе приложение успеет прочитать старые
  данные.
- **Никаких зависимостей между тестами.** Тест, работающий только после другого теста,
  переписывается.
- **Даты не берутся из «сегодня» вслепую.** Проверки «вчера / сегодня / завтра»
  считаются от текущей даты вычислением, а не константой в коде: константа протухнет
  и тест начнёт падать не по дефекту.
- **Ширина окна задаётся явно** в каждом тесте через фикстуру: 1280×800 либо 375×812.
  Ширина — часть условий проверки, а не деталь окружения.
- Если тест дал разный результат на двух прогонах — он не «иногда падает», он сломан.
  Разобраться до того, как записывать находку.

## Что автоматизируется в первую очередь

Автоматизация окупается на повторяемом и на точном.

- **Окупается:** арифметика итогов и округление, доли в легенде, границы сумм и длин
  парами, отсутствие записи после отклонённой формы, цикл «сохранить → загрузить»
  с грязными значениями, валидация данных, пришедших из CSV, ошибки в консоли.
- **Дешевле руками:** одноразовые визуальные наблюдения, вёрстка, удобство,
  «понятно ли новичку», читаемость легенды на тридцати категориях.

Группа проверок «валидация при импорте» (каталог ручных проверок, `IMP-11 … IMP-15`)
автоматизируется в первую очередь: она требует подготовленных файлов и точного сравнения,
руками её проходить долго и легко ошибиться.

## Покрытие

Считается не по строкам кода объекта, а по спецификации:

- каждый из 16 пунктов таблицы ожиданий `SPEC.md` — минимум один автотест, если область
  вообще автоматизируема;
- каждая граница — параметризованной парой значений;
- пункты, оставленные ручной проверке, перечисляются явно с причиной.

В конце прогона в отчёте называется: сколько тестов, сколько прошло, сколько упало
и какой пункт `SPEC.md` закрывает каждое падение.

## Отчёт о прогоне

- Вывод `pytest` приводится **целиком, включая падения**. Падения не пересказываются
  своими словами: пересказ — это уже интерпретация.
- Каждый падающий тест сослан на номер `BUG-NNN`, а `BUG-NNN` — на пункт `SPEC.md`.
- Красный прогон показывается до любых разговоров о починке: починка объекта —
  это роль Автора и отдельная сессия.
- После прогона — `git status --short app/`, он должен быть пуст. Прогон тестов
  не имеет права изменить объект; если изменил — это находка серьёзнее прочих.
