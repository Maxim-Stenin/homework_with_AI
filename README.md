# Домашнее задание, направление QA: проверка продукта, который сделал агент

Задание 4. Работа состоит из двух разных вещей, и путать их нельзя:

- **Объект тестирования** — маленькое web-приложение «Мои финансы». Заказано агенту одной
  сессией по короткому описанию и после этого руками не правилось.
- **Материалы тестирования** — спецификация, тест-план, баг-репорты, автотесты, протокол
  расхождений, независимое ревью, исправленная копия. Это и есть сдаваемая работа.

Объект — один самодостаточный файл: HTML, CSS и JavaScript, без фреймворков, сборки
и сетевых запросов. Данные живут в `localStorage` браузера.

---

## Быстрый старт

Нужен только Python 3.14.7 — он уже установлен. Всё остальное ставится двумя командами.

### 1. Поднять стенд

Из корня проекта, в отдельном окне терминала:

```bash
py -m http.server 8080 --directory app --bind 127.0.0.1
```

Проверить, что стенд жив — **по ответу, а не по факту запуска**:

```bash
curl -si http://127.0.0.1:8080/index.html | head -1
```

Ожидается `HTTP/1.0 200 OK`. Страница открывается по адресу
<http://127.0.0.1:8080/index.html>.

> **Почему `py`, а не `python`.** В PATH Windows лежит заглушка Python из Microsoft Store:
> на `python --version` она отвечает словом `Python` без номера и кодом выхода 49.
> Лаунчер `py` находит настоящий интерпретатор. Ответ без номера версии означает заглушку,
> а не установленный Python.

> **Открывать файл двойным кликом не нужно.** Под Playwright и браузерными агентами
> протокол `file://` заблокирован — страница просто не откроется. Стенд поднимается
> сервером.

### 2. Поставить инструменты тестирования

Однократно:

```bash
py -m pip install pytest pytest-playwright
```

```bash
py -m playwright install chromium
```

Проверить: `py -m pytest --version` → `pytest 9.1.1`.

Версии, на которых всё прогонялось: pytest 9.1.1, pytest-playwright 0.9.0,
Playwright 1.62.0, Chromium 151.0.7922.34.

### 3. Прогнать автотесты

Стенд из шага 1 должен быть **уже поднят** — тесты его не запускают. Если стенда нет,
прогон останавливается с понятным сообщением, а не поднимает свой сервер на соседнем порту.

```bash
py -m pytest tests -v
```

**Ожидаемый результат: 78 тестов проходят, 37 падают.** Это норма, а не поломка.
Падения — реальные дефекты объекта; красный тест здесь и есть доказательство находки.
Разбор каждого падения — в `full-run/bugs.md`. `xfail` не используется намеренно:
он превратил бы находку в зелёную строчку.

## Прогон по исправленной копии

В `app-fixed/index_refactor.html` лежит копия объекта, в которой закрыты найденные дефекты.

Остановить стенд из шага 1 и поднять его же на другой папке — порт тот же:


### Старый набор по новой версии — измерение «что стало со вчерашними тестами»

```bash
APP_URL=http://127.0.0.1:8080/index_refactor.html py -m pytest tests -v
```

**Ожидаемый результат: 104 проходят, 11 падают** (на исходном объекте было 78 / 37).
Одна и та же папка `tests/` идёт против обеих версий, различие — один аргумент
`--directory` и одна переменная окружения. Так разницу в результатах нельзя списать
на разные наборы тестов или разные стенды.

Из этих 11 падений **ни одно не означает «фикс не сработал»**: все они разобраны
поимённо в `retest-run/README.md` и оказались устаревшими тестами — в фиксе появились

## Наивный прогон против прогона со спекой

Объект проверялся трижды: два прогона вслепую (`naive-run/`, `naive-run-2/`) и один
со спецификацией, правилами и скиллами (`full-run/`). Сравнение — самое интересное
место работы, потому что оно показывает, что даёт спека, а что она отнимает.

| | naive-run (сессия 5) | naive-run-2 (сессия 6) | full-run (сессия 6) |
|---|---|---|---|
| Что было доступно | код объекта, без `SPEC.md` | **ничего**, кроме работающей страницы | `SPEC.md`, `AGENTS.md`, оба скилла |
| Метод | белый ящик | чёрный ящик | чёрный ящик по тест-плану |
| Находок | 12 | 15 | 14 багов + 6 замечаний |
| Проверок оформлено | нет тест-плана | нет тест-плана | **137** |
| Автотесты | нет | нет | **115** |
| Артефакты | нет скриншотов | нет скриншотов | 12 снимков, 3 видео |
| Ложных находок | — | **3 из 15 (20 %)** | **1 из 15**, и её нашёл сам агент |

### Что получилось в наивном

Наивные прогоны нашли **почти всё крупное** — и нашли это быстро. Оба независимо
пришли к одному и тому же блокеру: загрузка постороннего файла молча стирает историю.
Оба увидели отрицательные суммы из CSV, суммы меньше копейки, слияние категорий
по регистру, удаление без подтверждения, вёрстку, разъезжающуюся на длинной строке.
Второй прогон получил это **не видя ни строки кода** — только интерфейс, `localStorage`
и выгружаемый CSV.

Сильная сторона наивного взгляда — **оракул «обещание на экране»**. Под таблицей
приложение пишет: файл «можно открыть в Excel и вернуть обратно». Наивный прогон
проверил это буквально: разделитель `,` вместо `;` для русской локали, десятичная
точка вместо запятой — Excel кладёт всю строку в одну колонку и читает суммы как текст.
А файл, пересохранённый русским Excel'ем, при обратной загрузке даёт ноль строк
и пустые итоги: тот же блокер, но **на собственных данных пользователя и точно
по инструкции, напечатанной в интерфейсе**. Прогон со спекой этот сценарий не нашёл —
в `SPEC.md` про Excel ничего не сказано, а тест-план строился от спеки.

Слабая сторона — **вердикты не на что опереть**. Без части А `SPEC.md` у наивного
прогона остаются только внутренняя согласованность, обратимость и здравый смысл.
Поэтому обе папки помечают часть находок как спорные (`BUG-009…012` в первой,
`BUG-012…015` во второй): «может, автор так и задумал». Верхнюю границу суммы наивный
прогон описал как «границы нет вообще» — назвать `99 999 999` он не мог, этого числа
нет нигде, кроме спеки. И цена спешки видна в цифрах: **три находки из пятнадцати
во втором прогоне не воспроизвелись** (Enter не отправляет форму; дата не подставляется;
нет BOM в файле — BOM на самом деле есть, `EF BB BF`). В прогоне со спекой ложной
оказалась одна из пятнадцати.

### Что изменилось после спеки

Появилось то, чего наивный взгляд не даёт в принципе — **границы парами**. `99999999`
проходит, `100000000` отклоняется; 32 символа проходят, 33 отклоняются; вчера проходит,
завтра отклоняется. Наивный прогон вообще не поднимал вопрос дат будущим числом:
без пункта 7 неоткуда узнать, что будущее запрещено. Пустую категорию, молча
превращающуюся в «Без категории», наивный прогон дефектом не считал — спека
(пункт 5) сделала её дефектом.

Появились **доказательства**. У наивных прогонов нет ни одного скриншота: в первом
браузерная панель не писала кадры на диск, во втором не отрисовывалась вовсе.
Оба честно это назвали и заменили картинки геометрией DOM — но проверяющему
предъявить нечего. Прогон со спекой дал 12 снимков, 3 видео и 115 автотестов,
из которых 37 красных — каждый красный и есть доказательство находки.

И появилась **воспроизводимость**. Наивная находка живёт абзацем в отчёте; находка
из полного прогона живёт проверкой `TC-NNN` с входом и ожидаемым результатом плюс
автотестом, который можно перезапустить через месяц. Именно это позволило сессии 9
измерить фикс: 37 красных тестов позеленели, и это факт, а не впечатление.

### Что спека отняла

Обратная сторона, и она дороже, чем кажется. **Тест-план строился от спеки — и там,
где спека молчит, проверок не появилось.** Четыре находки наивных прогонов
в `full-run/bugs.md` не попали, и их пришлось ловить заново ревьюеру в сессии 7:

| Находка наивного прогона | Что стало в полном прогоне |
|---|---|
| Битые строки CSV отбрасываются молча (naive-1, BUG-005) | нет; переоткрыто ревью как **R1**, критический |
| `12abc` принимается как 12 (naive-1, BUG-003) | нет; переоткрыто как **R3** |
| Длинный комментарий рвёт вёрстку, `scrollWidth` 2315 при окне 820 (naive-1, BUG-007) | **записано как ✅ пройдено** (TC-065) — проверяли, цел ли текст, а не цела ли страница |
| Подпись кольца 133 px против ~106 px отверстия (naive-1, BUG-012) | **записано как ✅** (TC-088) — сравнили с внешним диаметром 200 px |

Два последних случая — не пропуск, а **обратный вердикт**: наивный прогон посчитал
геометрию верно, а прогон со спекой записал «помещается» и закрепил это зелёным
автотестом. Разбор — в `claims-vs-facts.md`, случаи 1 и 2.

Причина не в спеке как таковой, а в том, **как с ней обошлись**: в сессии 6 наивные
папки закрыли от агента запретом — и закрыли **до** сверки находок с итоговым списком.
Двадцать семь уже записанных находок стали недоступны ровно тогда, когда их надо было
сверять. Это разобрано в `review/results.md`, E8, и это главный процессный урок работы.

**Вывод.** Наивный прогон дёшев, быстр и находит крупное — но не отличает дефект
от замысла и не оставляет доказательств. Прогон со спекой даёт границы, артефакты
и воспроизводимость — но видит ровно то, что записано в спеке, и слепнет там, где она
молчит. Порядок «сначала наивный, потом со спекой» верен; ошибка была в том,
что между ними не сделали сверку.

## Как велась работа

Девять сессий, журнал на каждую. Ключевое из правил проекта:

- **Роль называется в начале сессии.** Автор пишет код объекта и не проверяет его сам;
  Тестировщик проверяет и **не правит код ни при каких обстоятельствах**; Ревьюер проверяет
  работу Тестировщика. Разделение не формальность: проверяя там же, где писался код,
  проверяешь память агента, а не страницу.
- **Запреты продублированы механизмом.** Правило в файле — просьба, `deny`
  в `.claude/settings.json` — механизм. Запись в `app/` и `app-fixed/` заблокирована
  инструментом, контрольные пробы упираются в отказ.
- **Найденный баг не чинится и не удаляется.** BUG-006 позже оказался невоспроизводимым —
  запись осталась на месте, сверху лёг разбор ошибки тестировщика.
- **Фикс проверяет не тот, кто его писал.** Автор собрал исправленную копию в сессии 8
  и не прогонял по ней тест-план; ретест — сессия 9 и роль Тестировщика. Фикс,
  проверенный тем же агентом в той же сессии, доказывает лишь то, что агент помнит,
  что чинил.
- **«Готово» без вывода команды не считается.** К каждому утверждению о пройденной
  проверке приложен артефакт.

Полностью — в `AGENTS.md`.

## Что не сделано

Список честный и повторяется здесь, потому что умолчание о непроверенном равносильно
ложному отчёту.

- **`RT-BUG-001` не починен.** Дефект найден на исправленной копии и остался в ней:
  чинить его в роли Тестировщика запрещено, а сессии Автора после ретеста не было.
  Это значит, что BUG-011 закрыт не полностью — класс дефекта сужен, но не устранён.
- **Сохранность `localStorage` на исправленной копии не проверялась вовсе.** Крупнейшая
  дыра ретеста: фикс переписал путь импорта целиком, а именно импорт пишет в хранилище.
  В сессии 7 ревьюер проверил хранилище на **исходном** объекте, и там оно работало, —
  на исправленную копию этот результат не переносится.
- **Находки ревью R1…R4 не перенесены в `full-run/bugs.md`.** В документах ретеста они
  учтены полностью (`retest-run/discrepancies.md`), в документах исходного прогона — нет.
- **Правки по `review/results.md` сделаны частично.** Порог из E3 исправлен в `tests-fixed/`,
